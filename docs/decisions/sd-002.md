# SD-002 Architecture at a glance

Status: Agreed (decision log, 2026-10-13).

Recommendation: one FastAPI service owns the domain logic; the MCP server imports that same service layer in-process, and every model call runs in a background worker.

*(Diagram in the live decision log: SD architecture, 8 components.)*

Agents and people enter through different doors and land on the same service layer; the worker is the only component that talks to a model, so a slow or dead model never blocks a save. Public readers hit three read-only routes with no auth.

**Options considered.**

| Option | Shape | Why not |
|---|---|---|
| A. Modular monolith, MCP in-process | One repo, one deploy, MCP tools call the service functions directly | Recommended |
| B. MCP as a separate HTTP client of the API | MCP process holds a token and calls the REST API | Doubles the auth and error paths with no quick wins |
| C. Model calls inline in the request | Save waits for summary and tags | A 3B model on CPU takes 5 to 20 s; agents would time out |

**Consequences.** A page save returns at once with summary and tags marked pending; the worker fills them and bumps the page version. Self-hosters run three containers (api, worker, db) plus an optional Ollama. The MCP server can run over stdio for Claude Code and over HTTP for remote agents with the same tool code.

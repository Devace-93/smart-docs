# SD-012 File storage

Status: Agreed (decision log, 2026-10-13). Not built yet (EP-13).

Recommendation: keep attachment metadata in Postgres and the bytes behind one small storage interface, local disk by default and any S3-compatible bucket by env var.

**Context.** EP-13 moved into the MVP: pages take images and attachments. Self-hosters must run with no cloud account; the hosted instance serves images on public pages, where egress cost matters more than storage.

**Options considered.**

| Option | Shape | Why not |
|---|---|---|
| A. Storage adapter: local disk default, S3-compatible by config | put, get, delete, url behind STORAGE_BACKEND=local or s3; boto3 for the S3 side | Recommended |
| B. Local disk only | Files on a Docker volume | Hosted instance cannot survive a redeploy or scale past one box |
| C. S3 only | Every install needs a bucket and keys | Blocks clone-and-run self-hosting |
| D. fsspec or fastapi-storages | Library adapter over many backends | An extra dependency for about 40 lines Enrique would rather own and explain |

**Hosted bucket.** Cloudflare R2 (10 GB free, zero egress) for the hosted instance; Backblaze B2 (10 GB free) or Oracle Always Free (20 GB) as fallbacks; MinIO in Compose only to test the S3 path locally. Free tiers as of October 2026, to verify before setup.

**Consequences.** Attachment(id, page_id, filename, mime, size, storage_key) joins the data model; routes and MCP tools know only storage_key. Switching backends later is an env change plus a file copy. Public pages serve files through the API on local disk, or through a public or signed URL on S3.

**Decision:** Enrique sets the status in the index.

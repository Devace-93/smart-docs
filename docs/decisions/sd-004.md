# SD-004 Data model

Status: Agreed (decision log, 2026-10-13).

Recommendation: six tables, one tree per project held by `parent_id` plus a materialized `path`, and the page body split from the node so folders and pages share one tree.

*(Diagram in the live decision log: SD data model · 6 tables)*

A project owns a tree of nodes; a node is a folder or a page, and only page nodes carry a Page row with the Markdown, its rendered HTML, the model-written summary and tags, and the embedding. Public visibility is a flag on the page node; nothing is inherited from folders, so publishing one page never exposes its siblings.

**Options considered.**

| Option | Why not |
|---|---|
| A. Adjacency list (`parent_id`) plus materialized `path` | Recommended: simple writes, one indexed lookup for public URLs, cheap subtree listing with a prefix match |
| B. Closure table | Correct but heavier writes; the MVP has no deep queries that need it |
| C. Nested sets | Every move rewrites half the tree; agents move nodes often |
| D. One `documents` table, folders as pages without body | Fewer tables, but every page query filters on kind and public routes get messy |

**Rules.** `slug` is unique among siblings, `path` is unique per project. A move rewrites `path` for the subtree in one transaction. Soft delete via `deleted_at`; public routes and search ignore deleted rows. `version` is returned on every write so agents can send `If-Match` and avoid clobbering each other.

**Consequences.** Search is `ORDER BY embedding <=> query LIMIT k` inside one project with pgvector's HNSW index. Enrichment state lives on the page so the worker can retry failed rows and the API can show pending ones. Migrations start at 001 with Alembic; no table is created outside a migration.

**Decision:** Enrique sets the status in the index.
